# Step 21: AI Execution Replay & Debugging Studio Architecture

## 1. Overview & Core Mission

The **AI Execution Replay & Debugging Studio** provides deterministic inspection, safe re-execution, comparative diffing, and root-cause failure analysis for AI workflows, runs, and individual execution steps across the AI Work Layer platform.

The system systematically answers two critical production questions:
1. > *"What exactly happened during this AI execution?"*
2. > *"Can I reproduce, inspect, compare, and debug the execution safely?"*

## 3. Execution Snapshots

An execution replay operates exclusively on a deterministic snapshot of the original execution configuration, preventing mutation or drift from the source entity.

### Snapshot Schema (`ExecutionSnapshot`)
- `snapshot_version`: Schema version (default `"1.0"`).
- `run_id`: Original Run identifier.
- `workflow_run_id`: Associated Workflow Run identifier if applicable.
- `task_id`: Task identifier.
- `workspace_id`: Enforced tenant workspace boundary.
- `project_id`: Optional project scoping.
- `task_configuration`: Safe copy of task instructions, requirements, and prompts.
- `execution_requirements`: Persisted requirements generated by Task Intelligence.
- `model_configuration`: Model name, provider, temperature, max tokens.
- `retrieval_configuration`: Retrieval mode, collection IDs, top-k.
- `tool_configuration`: Enabled tool definitions and permission scopes.
- `connector_configuration`: Connector IDs, resource types, and operation scopes.
- `memory_configuration`: Memory retrieval parameters and namespace settings.
- `evaluation_configuration`: Evaluation metrics, threshold scores, and criteria.
- `workflow_version`: Workflow schema version if executed within a workflow.
- `relevant_context_metadata`: Persisted context summaries and chunk references (no raw sensitive blobs).
- `trace_metadata`: Normalized metadata from original execution spans.
- `created_at`: UTC timestamp of snapshot generation.

## 4. Snapshot Sanitization & Redaction

Before any snapshot is created, persisted, or displayed, it is processed through `sanitize_replay_snapshot()`:
- **Maximum Snapshot Payload**: Strictly enforced by `MAX_REPLAY_SNAPSHOT_BYTES = 5,000,000` (5MB). Over-limit payloads raise `ReplaySnapshotError`.
- **Sensitive Key Patterns**: Any dictionary key matching credentials (`api_key`, `secret`, `password`, `token`, `authorization`, `cookie`, `private_key`, `access_token`, `refresh_token`, etc.) is replaced with `"[REDACTED]"`.
- **Pattern Matching**: Regex sweeps detect and redact:
  - OpenAI/Anthropic/Provider API keys (`sk-...`)
  - Bearer tokens (`Bearer ...`)
  - Private key headers (`-----BEGIN ... PRIVATE KEY-----`)
  - Database connection strings (`postgres://...`, `mysql://...`, `mongodb://...`)
  - JSON Web Tokens (`eyJ...`)
- **Large Content Bounds**: Prompt strings and context chunks exceeding 64KB are cleanly truncated with `[TRUNCATED: ...]`.

## 5. Replay Modes

| Mode | Side Effects Executed | AI Provider Called | Purpose |
| :--- | :---: | :---: | :--- |
| `inspect` | ❌ No | ❌ No | Instant, read-only analysis of past execution trace, steps, and snapshot configuration without incurring cost or network calls. |
| `dry_run` *(Default)* | ❌ No | Optional (Mocked / Safe) | Full replay simulation where tool, connector, and memory mutations are intercepted and marked as simulated side-effects. |
| `replay` | ⚠️ Fresh HITL Only | ✅ Yes | Full re-execution of AI inference and read operations. Write/destructive actions require fresh, interactive HITL approvals. |
| `compare` | ❌ No | ❌ No | Deep factual differential analysis between the original run and a previously executed replay run. |

---

## 6. Side-Effect Policy & Isolation

External side effects fall into three categories:
1. **READ Operations**: (e.g. `github_read_issue`, `search_documents`, `fetch_metrics`). Eligible to run in live replay if current user credentials and permissions allow.
2. **WRITE Operations**: (e.g. `github_create_issue`, `update_record`, `send_notification`). Default to **BLOCKED/DRY-RUN**. In dry-run mode, the engine produces:
   ```json
   {
     "status": "simulated",
     "simulated": true,
     "message": "Would execute GitHub create issue (dry-run mode)"
   }
   ```
3. **DESTRUCTIVE Operations**: (e.g. `delete_branch`, `drop_table`, `revoke_access`). **ALWAYS** blocked during replay unless a fresh Human-in-the-Loop (HITL) confirmation is explicitly submitted and approved.

### Historical Approval Invariant
> [!CAUTION]
> **Approvals are NEVER reused.**
> An approval granted during the original run was context-dependent and time-bound. Replays must never inherit historical approvals. Every state-changing write requires a distinct, fresh approval request in the current execution context.

## 7. Replay Eligibility Verification

Before initiating any replay or dry run, `ReplayEligibilityChecker` verifies:
1. **Run Existence & Accessibility**: The run exists and the caller belongs to the target `workspace_id`.
2. **Associated Entities**: The parent task, project, and workflow (if applicable) have not been deleted.
3. **Workflow Version**: If replaying a workflow, the recorded workflow version must be present in the version history.
4. **Model Availability**: The specified model and provider are active and registered in `default_provider_registry`.
5. **Tool & Connector Access**: Required tools and connectors are still registered and enabled for the workspace.
6. **Snapshot Integrity**: The snapshot can be successfully parsed and passes all schema and security invariants.

If any check fails, the system returns `eligible: false` with specific warning diagnostics (e.g. `"The original model 'gpt-4-0314' is no longer available in this workspace"`).

## 8. Subsystem Replay Behaviors

### Connector Replay
- Read connectors evaluate against current workspace authorizations.
- Write connectors default to dry-run simulation.
- Replay UI explicitly displays: *"External data may differ from the original run."*

### Tool Replay
- Read-only tools execute according to existing `ToolExecutor` rules.
- Write/mutating tools output dry-run execution results.
- Destructive tools require fresh HITL gating.

### Memory Replay
- Memory retrieval uses current authorization and namespace parameters.
- Memory creations, updates, or deletions are simulated in dry-run mode (`"Would create memory: key=..."`).
- Never silently mutates persistent memory during debugging runs.

### Evaluation Replay
- Re-executes factual evaluators: grounding, completeness, citation accuracy, formatting, and safety checks.
- Produces direct, factual comparisons against the original run's evaluation metrics.
- Evaluator outputs are compared without computing subjective aggregate scores.

## 9. Output Comparison & Diff View

`ReplayComparator` provides factual differential reporting across:
- **Output Difference**: Character, word, and unified line diffs highlighting added and removed content.
- **Model Difference**: Changes in model, provider, temperature, or prompt formatting.
- **Usage & Cost Deltas**: Input token delta, output token delta, cost delta ($USD), and latency delta (ms).
- **Context & Citations**: Additions and omissions of document source IDs, titles, and retrieval similarity scores.
- **Evaluation Findings**: Differences in detected hallucinations, missing citations, or safety warnings.
- **Reproducibility & Determinism Indicators**:
  - `same_model`: Boolean
  - `same_workflow_version`: Boolean
  - `same_retrieval_strategy`: Boolean
  - `reproducibility_note`: Explicit disclaimer:
    > *"Replay may differ from the original because model responses, external data, and provider behavior can change."*

## 10. Observability & Telemetry Integration

The replay subsystem fully reuses the existing `ExecutionTracer` and `observability_service` infrastructure:
- **Extended Event Types**:
  - `REPLAY_STARTED`: Emitted upon queueing/execution start with snapshot version and mode.
  - `REPLAY_COMPLETED`: Emitted with completion metrics, diff stats, and execution step count.
  - `REPLAY_FAILED`: Emitted with normalized error code and diagnostic insights.
  - `REPLAY_CANCELLED`: Emitted when cooperative cancellation is requested.
  - `REPLAY_SIDE_EFFECT_BLOCKED`: Emitted whenever a write or destructive action is diverted to dry-run simulation.
- **Metadata Tagging**: All trace events within a replay run include `replay_id`, `original_run_id`, `replay_mode`, `dry_run: true/false`, and `modified_configuration`.

---

## 11. Error Classification & Diagnostic Insights

When an original run fails, `ErrorAnalysisService` produces factual, structured diagnostics:
- **Failure Classification Categories**:
  - `MODEL`: Context window exceeded, invalid stop sequences.
  - `PROVIDER`: Rate limit, authentication, provider 5xx, or provider timeout.
  - `RETRIEVAL`: Vector store unavailable, zero matches found.
  - `TOOL`: Tool execution error, permission denied.
  - `CONNECTOR`: External auth expired, connector unreachable.
  - `WORKFLOW`: Step prerequisite failed, cyclic dependency.
  - `EVALUATION`: Safety check failed, grounding threshold breach.
  - `TIMEOUT`: Execution deadline exceeded.
- **Actionable Suggestions**: Suggests deterministic next steps without subjective model praise (e.g. *"Replay in dry-run mode with retrieval top_k adjusted to 3"* or *"Replay with another compatible provider model"*).

---

## 12. Security & Integrity Guarantees

1. **Original Run Immutability**: Original runs, workflow runs, and their trace events are strictly read-only and never modified by replays.
2. **Distinct Replay Runs**: Every replay is stored in a dedicated `replay_runs` database record with clear lineage (`original_run_id`, `replay_snapshot_version`, `created_by`).
3. **Workspace Isolation**: Replay creation, inspection, and step re-execution strictly require authenticated membership in the run's workspace.
4. **No Secrets Persistence**: API keys, tokens, and authorization headers are scrubbed during snapshotting and never saved in `replay_runs.snapshot`.
5. **No Chain-of-Thought Exposure**: Replays do not store, expose, or reconstruct hidden reasoning tokens.
6. **No Subjective Ranking**: Comparisons present factual, measurable deltas (tokens, latency, text diffs) rather than arbitrary quality rankings.
